40만 자 문서 하나가 서버를 세우던 이유: 라씨 성능 개선 기록

라씨는 미리보기의 쪽 경계를 내려받을 PDF 와 똑같이 맞추려고, 글을 고칠 때마다 서버가 PDF 를 실제로 그려 봐요. 그런데 40만 자 문서를 고치는 사람 한 명이 같은 서버를 쓰는 모두의 미리보기를 붙잡고 있었어요. 무엇이 무거웠고 어떻게 줄였는지 정리했어요.

2026년 11월 26일 · 와타랩스

입력 지연에는 자동화 도구의 왕복 약 25~30ms 가 들어 있어요. 요청 크기는 같은 단락이 반복되는 시험 문서 기준이라 실제 문서는 덜 줄 수 있어요.

무엇이 무거웠나: 프로파일로 찾은 네 가지

  1. 쪽 위치만 필요한데 PDF 를 끝까지 그렸어요. 20만 자 문서의 쪽 계산 3.1초 가운데 글·표 그리기가 1.1초, PDF 파일 만들기(글꼴 넣기·인코딩)가 0.3초를 넘었어요.
  2. 같은 글을 두 번 읽었어요. 미리보기 요청에서 한 번, 쪽 계산 요청에서 또 한 번. 40만 자 파싱 0.54초의 70%는 줄마다 서식을 표준 꼴로 다듬는 일이었어요.
  3. 렌더가 전역 잠금 안에서 돌았어요. 한 사람의 2.4초짜리 쪽 계산 동안 같은 서버의 다른 사람 미리보기와 PDF 가 줄을 서야 했어요.
  4. 요청이 컸어요. 글에 기준 문서와 직전 문서(JSON)를 함께 실어, 미리보기 요청 하나가 2.85MB 였어요. 업로드가 느린 망에서는 멈출 때마다 몇 초씩 걸렸어요.

서버: 그리지 않고 배치만, 바뀐 줄만 다시

  • 배치만 하는 쪽 계산 — reportlab 에서 글이 놓일 자리는 wrap·split 이 정하고, 그리기(drawOn)는 칠하기만 해요. 쪽 계산 때는 그리기를 잠시 빈 함수로 바꾸고 PDF 저장을 건너뛰는 캔버스를 써요. 40만 자 쪽 계산이 2.36초에서 1.29초가 됐어요.
  • 줄 단위 서식 캐시 — 서식 다듬기는 문자열만 받는 순수 함수라 줄마다 결과를 기억해요. 고치는 동안 대부분의 줄은 그대로라 다음 되읽기는 바뀐 줄만 계산해요. 400자 이하 줄 32,768개까지만 담아 메모리를 묶어 뒀어요.
  • 같은 요청은 다시 안 함 — 문서·설정·그림 크기가 같으면 앞서 낸 쪽 배치를 돌려줘요. 미리보기를 껐다 켜는 경우 2.4초가 7ms 가 됐어요.
  • 요청 gzip — 64KB 넘는 요청은 브라우저의 CompressionStream 으로 줄여 보내고 서버 미들웨어가 풀어요. 풀린 크기도 본문 한도를 넘지 못하게 해 압축 폭탄을 막았어요.

브라우저: 고치지 않은 블록은 다시 변환하지 않기

38만 자 문서에서 한 글자를 칠 때마다 두 가지가 문서 전체를 대상으로 돌고 있었어요. 편집기 문서를 마크다운으로 바꾸는 일(글자마다 약 39ms)과, 오른쪽 미리보기를 다시 그리는 일(약 51ms)이에요.

  • 구조 공유를 이용한 변환 캐시 — 편집기(ProseMirror)는 고치지 않은 노드를 다음 판에서도 같은 객체로 써요. 노드마다 JSON 을 WeakMap 에 기억하면 고치지 않은 문단·항목·표 칸은 같은 객체가 되고, 그 객체에 묶어 둔 변환 결과를 그대로 써요. 글자 하나 칠 때 바뀐 블록만 계산해요.
  • 기억은 편집기가 만든 객체에만 — 바깥에서 넘긴 JSON 은 나중에 바뀔 수 있어서 기억하지 않아요. 바깥에 내주는 문서는 복사본이라 기억해 둔 값이 오염되지 않아요.
  • 미리보기는 바뀐 게 없으면 그대로 — React.memo 로 감싸, 받는 값이 그대로면 다시 그리지 않아요.

이 변환 개선은 npm 패키지 @watalabs/lasee-mditor 0.2.1 에도 들어가, 라이브러리를 쓰는 쪽도 큰 문서에서 같은 효과를 봐요.

결과가 같은지 어떻게 지켰나

  • '배치만' 한 쪽 계산이 실제로 그린 PDF 의 배치와 같은지, 설정 4가지(글자 크기, 가로·Letter, 섹션마다 새 쪽, 다른 글꼴) × 문서 4가지로 시험해요.
  • 편집기 변환은 실제 편집처럼 30여 곳을 차례로 고치며, 기억을 쓴 결과와 새로 변환한 결과가 매번 같은지 봐요.
  • 깨진 압축 본문은 400, 풀면 한도를 넘는 압축 폭탄은 413 으로 거절하는지도 시험해요.

배운 것

지연은 큰 문서를 쓰는 사람만의 문제가 아니었어요. 공유하는 자원 위에서는 가장 무거운 사용자가 모두의 체감 속도를 정해요. 그리고 느린 곳은 짐작으로 찾지 않았어요. 매번 프로파일로 시간이 새는 곳을 먼저 보고, 고친 뒤에는 결과가 달라지지 않았다는 것을 시험으로 못 박았어요.
